# Goal
Generate a full POM-structured Playwright TypeScript test suite from ADO test scenarios and app analysis output. Produce three layers: Object Repository (locator files), Page Classes (action wrappers), and Spec files (scenario tests using page classes only).

# POM Layer Definitions

| Layer | Folder | File pattern | Responsibility |
|---|---|---|---|
| Object Repository | `locators/` | `<page>.locators.ts` | Pure `export const` locator constants. No Playwright imports. One file per page/component. |
| Page Classes | `pages/` | `<page>.page.ts` | TypeScript class that imports from its locator file and wraps every interaction as a named method. |
| Spec Files | `specs/` | `<story-kebab>.spec.ts` | `test()` blocks that import and instantiate page objects. Never contain raw selectors. |

# Inputs
- `test_scenarios` — from `ado-testcase-parser`
- `page_definitions` — from `playwright-app-analysis` (includes `locators`, `action_methods`, `page_file`, `locator_file` per page)
- `shared_component_locators` — from `playwright-app-analysis`
- `auth_pattern` — from `playwright-app-analysis`
- `story_title`
- `test_output_path` — root folder for all generated test files (e.g., `tests/e2e`)
- `report_output_path` — folder where Playwright HTML report is written (e.g., `playwright-report`)
- `screenshot_mode` — `all` | `on-failure` | `none` (default: `on-failure`)
- `log_level` — `step` | `action` | `none` (default: `step`)
- `spec_name_override` (optional)

# Prerequisites
- `APP_BASE_URL` is available (used as `baseURL` in test config).

# Generation Rules

## Test Config — `config/test-config.ts` *(generated first, before any spec or page class)*

Generate one `config/test-config.ts` under `test_output_path/config/`. This is the **single source of truth** for all runtime values used by specs and page classes. No spec or page file may read `process.env` directly — they must import from this file.

Rules:
- Define a `TestConfig` interface with all configurable runtime fields.
- Export a `config` const that reads each value from `process.env` via a `requireEnv()` guard that throws a descriptive error if a variable is missing.
- Include every value from `workflow-input.current.json` that tests may need: `baseUrl`, `username`, `password`, and any tenant/environment-specific values extracted from `raw_input_file` or ADO scenarios.
- This file is safe to commit — it contains no literal secrets, only `process.env` reads.
- Playwright loads values from a generated `.env` file (written by `preflight-guardrails.ps1`) via `dotenv` in `playwright.config.ts`.

```typescript
// config/test-config.ts
// Auto-generated by ui-testcase-orchestrator.
// All values are read from environment variables populated by preflight-guardrails.ps1.
// Do not hardcode credentials or URLs here.

export interface TestConfig {
  baseUrl:  string;
  username: string;
  password: string;
}

function requireEnv(name: string): string {
  const value = process.env[name];
  if (!value) {
    throw new Error(
      `[test-config] Required environment variable not set: ${name}\n` +
      `Run: pwsh ui/scripts/preflight-guardrails.ps1 to generate .env from workflow-input.current.json`
    );
  }
  return value;
}

export const config: TestConfig = {
  baseUrl:  requireEnv('APP_BASE_URL'),
  username: requireEnv('APP_USERNAME'),
  password: requireEnv('APP_PASSWORD'),
};
```

> If additional tenant/app-specific values (e.g., `TENANT_ID`, `API_KEY`) are present in `workflow-input.current.json` or the raw input file, add them as fields on `TestConfig` and corresponding `requireEnv()` calls.


- One file per page in `page_definitions`.
- Export a single `const` object named `<PageName>Locators` (e.g., `LoginLocators`).
- Each key is the `camelCase` locator name from analysis; each value is the selector string.
- Add one `shared-components.locators.ts` for locators in `shared_component_locators`.
- No Playwright imports in locator files.

Example:
```typescript
// locators/login.locators.ts
export const LoginLocators = {
  usernameInput: '[data-testid="username"]',
  passwordInput: '[data-testid="password"]',
  submitButton:  '[data-testid="login-submit"]',
  errorMessage:  '[data-testid="login-error"]',
} as const;
```

## Page Classes — `pages/<page>.page.ts`
- One class per page, named `<PageName>Page` (e.g., `LoginPage`).
- Constructor accepts Playwright `Page` as `private readonly page: Page`.
- Import locators only from the corresponding `locators/<page>.locators.ts`.
- Expose one `public` method per user-facing action in `page_definitions.action_methods`.
- Internal helpers (e.g., waiting for an element) must be `private`.
- `goto()` must use `this.page.goto(APP_BASE_URL + route)`.
- Never expose raw locator strings outside the class.
- All method parameters and return types must be explicitly typed — **no `any`**.
- Every public method must have a JSDoc comment stating the action, locator used, and any preconditions.
- Group methods with comment blocks: `// --- Navigation ---`, `// --- Form Inputs ---`, `// --- Assertions ---`.
- If two or more pages share a UI component, model it as a `<Component>Component` class (see Composition below).
- **When `log_level` is `action` or `step`:** add `console.log('[<PageName>] <methodName> — start')` as the first line and `console.log('[<PageName>] <methodName> — done')` as the last line of every public method.

Example (`log_level: action`):
```typescript
// pages/login.page.ts
import { Page, expect } from '@playwright/test';
import { LoginLocators } from '../locators/login.locators';

export class LoginPage {
  constructor(private readonly page: Page) {}

  // --- Navigation ---

  /**
   * Navigates to the login page.
   * Waits for the username input to be visible before returning.
   */
  async goto(): Promise<void> {
    console.log('[LoginPage] goto — start');
    await this.page.goto('/login');
    await this.page.locator(LoginLocators.usernameInput).waitFor({ state: 'visible' });
    console.log('[LoginPage] goto — done');
  }

  // --- Form Inputs ---

  /**
   * Fills the username field.
   * @param value - The username string to enter.
   * Locator: LoginLocators.usernameInput
   */
  async fillUsername(value: string): Promise<void> {
    console.log('[LoginPage] fillUsername — start');
    await this.page.fill(LoginLocators.usernameInput, value);
    console.log('[LoginPage] fillUsername — done');
  }

  /**
   * Fills the password field.
   * @param value - The password string to enter.
   * Locator: LoginLocators.passwordInput
   */
  async fillPassword(value: string): Promise<void> {
    console.log('[LoginPage] fillPassword — start');
    await this.page.fill(LoginLocators.passwordInput, value);
    console.log('[LoginPage] fillPassword — done');
  }

  /**
   * Clicks the login submit button.
   * Precondition: username and password fields must be filled.
   * Locator: LoginLocators.submitButton
   */
  async clickLogin(): Promise<void> {
    console.log('[LoginPage] clickLogin — start');
    await this.page.click(LoginLocators.submitButton);
    console.log('[LoginPage] clickLogin — done');
  }

  // --- Assertions ---

  /**
   * Returns the text content of the error message element, or null if absent.
   * Locator: LoginLocators.errorMessage
   */
  async getErrorMessage(): Promise<string | null> {
    console.log('[LoginPage] getErrorMessage — start');
    const text = await this.page.locator(LoginLocators.errorMessage).textContent();
    console.log('[LoginPage] getErrorMessage — done');
    return text;
  }

  /**
   * Asserts that the error message contains the expected substring.
   * @param substring - Expected error text fragment.
   */
  async assertErrorContains(substring: string): Promise<void> {
    await expect(this.page.locator(LoginLocators.errorMessage)).toContainText(substring);
  }
}
```

> **When `log_level` is `none`:** omit all `console.log` lines from page classes.

## Component Composition — shared UI components
When two or more pages share a visible component (navigation bar, modal, toast), model it as a component class:

```typescript
// pages/navigation.component.ts
import { Page } from '@playwright/test';
import { NavigationLocators } from '../locators/navigation.locators';

export class NavigationComponent {
  constructor(private readonly page: Page) {}

  /** Clicks the logout link in the top navigation bar. */
  async clickLogout(): Promise<void> {
    await this.page.click(NavigationLocators.logoutLink);
  }

  /** Returns the text of the logged-in user label. */
  async getLoggedInUser(): Promise<string | null> {
    return this.page.locator(NavigationLocators.userLabel).textContent();
  }
}
```

Page classes that include this component **compose** it:
```typescript
export class DashboardPage {
  readonly nav: NavigationComponent;

  constructor(private readonly page: Page) {
    this.nav = new NavigationComponent(page); // composition, not inheritance
  }
}
```

Specs access the component through the page object:
```typescript
await dashboardPage.nav.clickLogout();
```

## BasePage (use only when 3+ pages share logic)
If 3 or more pages share an identical method (e.g., `waitForPageLoad`, `dismissModal`), create an abstract base:
```typescript
// pages/base.page.ts
import { Page } from '@playwright/test';

export abstract class BasePage {
  constructor(protected readonly page: Page) {}

  /** Waits for the network to be idle and the page to be fully loaded. */
  async waitForPageLoad(): Promise<void> {
    await this.page.waitForLoadState('networkidle');
  }
}
```

Extend only from `BasePage`; never chain page class inheritance deeper than one level.

## Spec Files — `specs/<story-kebab>.spec.ts`
- One spec file per user story.
- Import and instantiate page objects — no raw selectors, no raw `page.*` calls.
- Group all `test()` blocks in a `test.describe('<story_title>', ...)` block.

### Single Sequential Flow (default)
- **By default, generate ONE single sequential `test()` block that runs all of the story's test cases in order as one end-to-end flow.** Do not create a separate `test()` per ADO test case unless a split is explicitly called for (see below).
- Inside that single `test()`, map each ADO test case to a top-level `test.step('<TC id> — <TC title>', async () => { ... })`, and each ADO step to a nested `test.step(...)`. Annotate each test-case step with its ADO TC ID in a comment.
- Order the test-case steps to preserve any required sequence — in whichever direction the scenario dictates (UI before a dependent API call, or API before a dependent UI check, and vice versa). The single-flow default guarantees this ordering under `fullyParallel: true`, which independent `test()` blocks cannot.

### When to split into multiple `test()` blocks (opt-in)
Produce multiple `test()` blocks **only when a split is explicitly called for**, i.e. any of:
- the workflow input / caller explicitly requests separate tests (e.g. a `test_split` / `split_tests` flag or an equivalent instruction), or
- an ADO test case is explicitly marked as independent / standalone, or
- the scenarios have genuinely no ordering dependency **and** the caller has asked for isolation/parallelism.

When splitting, still group all `test()` blocks under the same `test.describe('<story_title>', ...)`, and annotate each with its ADO TC ID.
- `beforeEach`: declare page object variables at describe scope; instantiate in `beforeEach`; run auth setup using the login page class if `auth_pattern` is not `none`.
- Use page class assertion methods (`assertErrorContains()`, `assertRedirectedTo()`) — not inline `expect(page.locator(...))`.
- Extract repeated test data (usernames, passwords, URLs) to a `const` block at the top of the file or to `fixtures/test-data.ts` if shared across specs.
- **Never read `process.env` directly in spec files** — always import from `../config/test-config`.
- **Wrap every logical step inside a `test.step('description', async () => { ... })` call.** This produces step-level output in the HTML report and trace viewer regardless of `log_level`.
- **Never embed literal host/URL, username, or password values in a `test.step()` title (or its `console.log`).** Step titles surface in the HTML report and step screenshots, and become stale/misleading when config changes. Describe the action generically and, when referring to a credential or URL, say it comes from config — e.g. `'Navigate to the application login page (URL from config)'`, `'Enter the Admin username (from config)'`, `'Enter the Admin password (from config)'`. ❌ `'Login into https://qa01.example.com/'`, `'Enter the username as admin'`, `'Enter the password as P@ss123'`. Do not include the config key name either (e.g. avoid `(config.password)`); use a plain description like `(from config)`.
- **The same rule applies to any sensitive, patron, or profile (PII) data** — e.g. patron/customer names, account/card/loyalty numbers, emails, phone numbers, addresses, dates of birth, government IDs, or payment details. Never place these literal values in a `test.step()` title, `console.log`, attachment name, or screenshot filename. Describe them generically and reference their source instead — e.g. `'Enter the patron account number (from test data)'`, `'Search for the patron (from config)'`, `'Fill the profile email (from test data)'`. ❌ `'Search for patron John Smith'`, `'Enter card number 6011...'`.
- **When `screenshot_mode` is `all`:** call `await page.screenshot({ path: \`test-results/screenshots/<test-name>-<step-name>.png\` })` as the last line inside every `test.step()` callback.
- **When `screenshot_mode` is `on-failure`:** do not add inline screenshot calls — Playwright config handles it via `screenshot: 'only-on-failure'`.
- **When `screenshot_mode` is `none`:** do not add any screenshot calls.
- **When `log_level` is `step` or `action`:** add `console.log('▶ <step description>')` as the first line of each `test.step()` callback.

Example (`screenshot_mode: all`, `log_level: step`):

      await page.screenshot({ path: 'test-results/screenshots/valid-login-dashboard.png' });

## Playwright Config — `playwright.config.ts`
Generate one `playwright.config.ts` at the **repo root** (not inside `test_output_path`).

Rules:
- Load environment variables from `.env` using `dotenv` at the top of the file. This `.env` is generated by `preflight-guardrails.ps1` from `workflow-input.current.json` and must be gitignored.
- `baseURL` must come from `config.baseUrl` imported from `<test_output_path>/config/test-config`.
- `testDir` must equal `test_output_path` (e.g., `'./tests/e2e'`).
- `outputDir` for test artifacts (screenshots, traces, videos) must be `'test-results'`.
- HTML reporter `outputFolder` must equal `report_output_path` (e.g., `'playwright-report'`).
- Always include JSON reporter at `test-results/results.json` and JUnit XML at `test-results/junit.xml` for CI/ADO pipeline consumption.
- `screenshot` value is driven by `screenshot_mode`:
  - `all` → `'on'`
  - `on-failure` → `'only-on-failure'`
  - `none` → `'off'`
- `trace` must always be `'on-first-retry'`.
- `video` must always be `'retain-on-failure'`.
- Only include the `chromium` project by default; the user can extend it.
- Set `open: 'never'` on the HTML reporter so CI does not try to open a browser.

Example (`screenshot_mode: on-failure`):
```typescript
// playwright.config.ts
import { defineConfig, devices } from '@playwright/test';
import 'dotenv/config';
import { config } from './tests/e2e/config/test-config';


export default defineConfig({
  testDir: './tests/e2e',
  outputDir: 'test-results',
  reporter: [
    ['html', { outputFolder: 'playwright-report', open: 'never' }],
    ['json', { outputFile: 'test-results/results.json' }],
    ['junit', { outputFile: 'test-results/junit.xml' }],
    ['list'],
  ],
  use: {
    baseURL: config.baseUrl,
    trace: 'on-first-retry',
    screenshot: 'only-on-failure',  // 'on' for all | 'off' for none
    video: 'retain-on-failure',
  },
  projects: [
    { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
  ],
});
```

> **Note**: `testDir`, HTML `outputFolder`, and `screenshot` are interpolated from `test_output_path`, `report_output_path`, and `screenshot_mode` in the workflow input. The `config` import path must be updated to match `test_output_path`. If `playwright.config.ts` already exists in the target repo, emit a warning in `conversion_warnings` and skip generation rather than overwriting it.

# Actions
0. **Generate `config/test-config.ts` first** (the config layer) — before any locator, page class, or spec file. This must exist before spec files that import from it.
1. For each page in `page_definitions`: generate its locator file and page class file.
2. Generate `locators/shared-components.locators.ts` from `shared_component_locators`.
3. Derive spec file name from `story_title` in kebab-case, unless `spec_name_override` is provided.
4. **By default, create ONE single sequential `test()` block** inside the spec's `test.describe` that runs every test scenario in order (each scenario as a top-level `test.step`). Create multiple `test()` blocks **only when a split is explicitly called for** (see Spec Files → *When to split*).
5. Map each scenario step to the appropriate page class method from `action_methods`.
6. Derive `expect()` calls from the scenario's `expected_result` field.
7. Emit `beforeEach` auth setup using the login page class when `auth_pattern` is not `none`.
8. Generate `playwright.config.ts` at repo root (with `dotenv` and `config` import) after all test files are generated.
9. **When `playwright_project_mode` is `new`**: generate `package.json` and `tsconfig.json` at repo root so developers can `npm install` and run tests immediately after copying files.

## Scaffolding Files — `package.json` and `tsconfig.json` *(only when `playwright_project_mode` is `new`)*

Generate these at the **repo root** alongside `playwright.config.ts`. Do not generate if `playwright_project_mode` is `existing`.

```json
// package.json
{
  "name": "<story-kebab-name>-playwright-tests",
  "version": "1.0.0",
  "private": true,
  "scripts": {
    "test": "npx playwright test",
    "test:headed": "npx playwright test --headed",
    "test:report": "npx playwright show-report playwright-report"
  },
  "devDependencies": {
    "@playwright/test": "^1.56.1",
    "@types/node": "^24.9.1",
    "dotenv": "^16.0.0"
  }
}
```

```json
// tsconfig.json
{
  "compilerOptions": {
    "target": "ES2020",
    "module": "commonjs",
    "strict": true,
    "esModuleInterop": true,
    "resolveJsonModule": true,
    "outDir": "dist",
    "types": ["node", "@playwright/test"]
  },
  "include": [
    "<test_output_path>/**/*.ts",
    "playwright.config.ts"
  ],
  "exclude": [
    "node_modules",
    "dist"
  ]

```

> Replace `<story-kebab-name>` with the kebab-case story title. Replace `<test_output_path>` with the value from workflow input (e.g., `tests/e2e`).

10. Write all generated files under `test_output_path`: `locators/`, `pages/`, `specs/`.

# Outputs
- `locator_files` — list of `{ file_path, locator_count, page_name }`
- `page_class_files` — list of `{ file_path, method_count, page_name }`
- `spec_files` — list of `{ file_path, test_count, scenario_ids[] }`
- `generated_file_contents` — full TypeScript source keyed by file path
- `conversion_warnings` — scenarios that could not be fully translated
