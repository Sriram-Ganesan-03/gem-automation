**Story intent:** As Venetian VConnect, retrieve the receipt for a successfully completed mobile offer redemption through a Connector proxy API, so Venetian Mobile can present the correct receipt without integrating directly with Trilogy. The endpoint retrieves the receipt **after** redemption; it never performs the redemption. Receipts with no email/SMS channel enter the existing player-receipt ingestion path; receipts requesting email/SMS are ingested by the existing distribute-receipt workflow; the same receipt must never be ingested twice.

## Requirement Analysis (Phase 0)

### Business Rules
- Authenticated Connector proxy endpoint lets approved VConnect integrations retrieve a redemption receipt from Trilogy.
- Retrieval is initiated only for a redemption VConnect reports as successfully completed; the original redemption is never re-executed.
- A returned receipt must belong exactly to the requested property, player, offer, and redemption transaction, with a stable Receipt ID.
- Requests flow through the approved Trilogy/property path; VConnect never connects to Trilogy directly; Connector never alters receipt content.
- No-email/SMS receipts → existing player-receipt ingestion (US 1445168). Email/SMS receipts → existing distribute-receipt workflow owns ingestion.
- The same receipt is never ingested/stored twice; retries are idempotent on redemption transaction + Receipt ID.
- Downstream Trilogy failures map to the approved Connector error format and never report false success.
- Authorization is enforced before returning any data; cross-property/cross-player access is rejected; sensitive data is not unnecessarily logged.

### Dependencies
- VConnect completing the original redemption and supplying correlation/reference data.
- Existing Trilogy Redeem Offer Receipt capability.
- US 1445168 and 1365562 for ingestion/storage.
- Approved Trilogy/property integration path.

### Constraints / Out of Scope
- Out of scope: offer list, offer detail, original redemption, mobile UI, receipt-list presentation, receipt HTML rendering, direct notification delivery.
- Distinct from US 1459617 (BeOn post-redemption availability signal/callback).

### Assumptions
- Proxy returns JSON (`Content-Type: application/json`).
- Approved error format is a structured Connector error body with a correlation id and no sensitive data.
- Delivery-channel configuration (email/SMS vs none) is available to route ingestion vs distribution.
- Receipt ID is the stable idempotency key across retries.
